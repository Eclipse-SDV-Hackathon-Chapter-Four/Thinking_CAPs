Thinking CAPs Eclipse contribution compliance audit

2026-10-07T10:49:47.205684+00:00

Not all contributions are ready or demonstrably compliant. Two published native PRs have failing ECA gates; policy/checklist, commit metadata, disclosure, IP-review and evidence issues remain.

Official Eclipse project requirements apply to native contributions. Thinking_CAPs is an event repository: its status as an official Foundation-managed project repository was not established. Foundation requirements are used as upstream readiness criteria for its integration code, not asserted as automatic legal violations for every hackathon commit. Team README review/transparency promises apply to its work.

The captured 24-issue registry (20 initially registered issues plus four communication bugs imported during the audit); selected current native patches and all referenced PR drafts; local and remote Git branch contribution records; GitHub native PRs #601/#40/#3307 and hackathon PRs #32/#33/#34; source notice scan outside imported evidence. No source code or original evidence was changed.

Findings and required corrections

F01 Two published upstream PRs fail Eclipse ECA validation

high | confirmed_failed_gate

GitHub reports eclipsefdn/eca=failure for CDA PR #601 and inc_diagnostics PR #40. The official Eclipse validation pages specifically report that the author and committer Eclipse accounts cannot be found for their erupuri identity/email. Their branch submission checklists nevertheless mark ECA as DONE. This is an account/commit eligibility failure, not proof that the person never signed an agreement under another identity.

Action: The contributor must resolve account/agreement/email eligibility and obtain a passing PR ECA status. Correct the checklists to reflect the actual gate until it passes.

Evidence: https://github.com/eclipse-opensovd/classic-diagnostic-adapter/pull/601; https://github.com/eclipse-score/inc_diagnostics/pull/40; eclipse-opensovd--classic-diagnostic-adapter-pr-601.json; eclipse-score--inc_diagnostics-pr-40.json

F02 Submission checklists incorrectly require no AI attribution

high | confirmed_incorrect_guideline

The CDA and diagnostics branch submission documents contain No AI Attribution= DONE / Clean commit message; the CDA checklist also calls No AI attribution=PASS. Neither retrieved upstream contribution guide requires hiding AI use. The published PRs and their commit messages contain no AI assistance disclosure. Significant AI use on these particular patches remains an authorship question, so missing disclosure is conditional; the written checklist rule is already wrong.

Action: Replace the invented no-attribution criterion with accurate AI disclosure. Establish whether meaningful AI was used and disclose it in the published contribution when applicable.

Evidence: origin/feature/cda-543-result-error-handling:contributions/cda-543-evidence/PR-543-contribution-checklist.md; origin/feature/cda-543-result-error-handling:contributions/cda-543-evidence/PR-543-submission.md; origin/feature/inc-diagnostics-16-sovd-adapter:contributions/inc-diagnostics-16-evidence/PR-16-submission.md

F03 AI tools are recorded as human coauthors

high | confirmed_metadata_gap_for_upstream

All five prepared Rust API mail patches (#1261, #250, #560, #781, #490) include Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. The hackathon Rust queue, ThreadX, X-COM and OpenBSW branch commits also use this trailer. Eclipse coauthor entries identify real contributors subject to agreement validation. These commits already disclose AI use; an Assisted-by trailer is the appropriate identity convention, not a legal AI coauthor.

Action: Use Assisted-by for AI tool identification in future/native submission commits. Preserve real human authors and historical evidence; do not silently rewrite shared history.

Evidence: patch-audit.json; hackathon-32-commits.json; hackathon-33-commits.json; git log --all

F04 AI disclosure does not consistently travel with native contributions

high | submission_readiness_gap

Known AI-assisted SOME/IP, lifecycle, communication #1265/#1167 and four bug-queue PR drafts omit an explicit assistance disclosure. All selected registered patches lack AI Disclosure/CC0-1.0 markers. Rust API mail messages do disclose DeepSeek and corrections in prose, which is positive. The lifecycle new macro is explicitly attributed to Fabro/Flash in its record but has only an Apache-2.0 header. Source files largely generated by AI need the handbook file disclosure treatment; the degree of generation must be confirmed per file. PR #3307 discusses AI tooling but does not explicitly disclose AI assistance in authoring that contribution.

Action: Add explicit tool/model disclosure to the intended native commits and PRs. Review new files for largely AI-generated content and apply the handbook header/disclosure example with the actual project licence. Do not relabel copied third-party code or blanket-convert the repository to CC0.

Evidence: patch-audit.json; bug-queue-audit.json; native-3307-commits.json; contributions/issues/eclipse-score/lifecycle/704/README.md

F05 Large native patches have no recorded Eclipse IP Team review

high | required_review_not_evidenced

Patch additions are SOME/IP #84: 3198; communication #1261: 2132; #250: 1544; #560: 1976; OpenBSW transportRouter: 2353. Published diagnostics PR #40 adds 1503 lines. No corresponding IP review reference was found in the inspected records. The old five diagnostics patches add 2012 lines in total, including lock changes; they are not the same payload as PR #40. Added-line totals flag review candidates, not a legal calculation of net new IP. Generated/repeated content and committer status require project disposition.

Action: Ask the relevant project committer to evaluate net new content and the applicable IP review requirement; record the review/request and approval before official merging. Do not treat tests or splitting one contribution into smaller commits as IP approval.

Evidence: patch-audit.json; openbsw-packet-check.json; eclipse-score--inc_diagnostics-pr-40.json; ip-review-search.json

F06 Diagnostics PR #40 lacks required DCO sign-offs

high | confirmed_native_commit_gap

All three commits in inc_diagnostics PR #40 have no Signed-off-by trailer. Its current CONTRIBUTION.md explicitly requires both ECA and DCO. The SOME/IP and lifecycle artifacts are plain uncommitted diffs: absent trailers there are preparation items, not defective existing commits. S-CORE PR #3307 has a Signed-off-by trailer. Communication CONTRIBUTING.md does not itself explicitly mandate DCO, so no blanket DCO failure is asserted for that module.

Action: The actual contributor must supply the required truthful DCO certification for the diagnostics commits. Include it in future SOME/IP/lifecycle commits when preparing their submissions.

Evidence: eclipse-score--inc_diagnostics-pr-40.json; native-guidance.json; native-3307-commits.json

F07 Author names and ECA coverage need checking per native commit

medium | identity_conformance_gap

Many root/prepared commits and PR #3307 use author name jnsagai; CDA #601 and diagnostics #40 use erupuri. Eclipse requires the author actual legal name and matching account email. These values look like login handles; they are not verified legal identities. The declared Eclipse username jnascimento6p0 has a current signed-ECA lookup result (HTTP 200). PR #3307 independently has a passing ECA check. Neither result validates every other contributor, every email, or the proposed AI coauthors.

Action: Use the responsible contributor legal name and registered email in native commits. Validate each native PR through its actual Eclipse ECA check rather than extending one username lookup to every contribution.

Evidence: eca-lookups.json; 3307-status.json; native-3307-commits.json; patch-audit.json

F10 The root licence is abbreviated and source headers are inconsistent

medium | confirmed_licensing_documentation_gap

Root LICENSE is a 15-line Apache notice, not the full Apache-2.0 terms; GitHub reports NOASSERTION for its detected licence. There is no root CONTRIBUTING file, including the inspected organization defaults. A scan of 111 tracked source/script files outside contribution/evidence imports found 68 without SPDX markers and no copyright ownership marker in their first 2500 characters. This set includes imported helper scripts and is not a declaration of authorship. In remote ThreadX PR #32, 3/19 added source/script files lack SPDX; in X-COM PR #33 all 9 inspected new Python files lack SPDX. Existing native S-CORE new-source headers are generally present. JSON configurations cannot use ordinary comment headers and need separate treatment.

Action: Supply the full intended licence and document contribution/AI/review requirements. Establish actual ownership/provenance before adding appropriate file notices. Preserve upstream MIT/Apache and other imported notices; use supported sidecars or licence metadata for formats without comments.

Evidence: LICENSE; owned-source-headers.json; 32-files-headers.json; 33-files-headers.json; native-guidance.json

F11 Independent human review is not consistently recorded

medium | human_review_not_evidenced

SOME/IP/lifecycle records contain scoped local owner approval, which is positive but not upstream committer acceptance. Communication implementations and assessments explicitly retain pending acceptance. ThreadX PR #32 was merged by its author jnsagai and has no GitHub review or issue-comment records; X-COM PR #33 and Rust queue PR #34 also have no review records at retrieval. A human merge identity does not establish that an agent merged automatically, and an empty GitHub review list does not disprove an offline review. Root README requires another team member for critical changes and explicit human review of AI-modified code.

Action: Retain a real reviewer identity, reviewed revision and decision, including the additional reviewer required for critical changes. Keep human approval before official merges; do not infer it from agent reviews or test passes.

Evidence: README.md; hackathon-32-reviews.json; hackathon-33-reviews.json; hackathon-34-reviews.json; contributions/communication-1167/submission/HUMAN-DISPOSITION.md

Audit limits

  • This is an evidence and process audit, not legal clearance or complete semantic code/security review.
  • Native builds, hardware campaigns and model calls were not rerun. Recorded successes are subject-bound historical evidence.
  • Workspace imports changed concurrently during the audit. Audited Git refs are captured in audit-subject.json; measured manifest outputs describe the bytes when checked, not an atomic snapshot of the final mutable workspace.
  • Employer approval, confidential/PII prompt handling, provider terms, training use, indemnity conditions, plagiarism filtering and all third-party provenance cannot be certified from these artifacts.
  • No evidence establishes automatic AI merging. Missing review records do not prove that an offline review never occurred.
  • Encryption/cryptography applicability, official project committer status and IP review exemptions require the receiving project disposition.
  • Hackathon eligibility and organizer submission rules were not assessed.
