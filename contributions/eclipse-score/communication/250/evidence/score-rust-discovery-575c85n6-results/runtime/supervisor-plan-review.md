## P1 — async Drop claim is stronger than the actual ownership shape

Plan lines 237–239 and 317 claim that the future always stops discovery when dropped. The existing `consumer.rs:953–965` starts native discovery before returning the outer `async move` block at line 966. The object with the StopFindService Drop implementation, `ServiceDiscoveryFuture`, is created at lines 971–977 only when the outer future is polled. `bridge_ffi.rs:340–365` wraps the native pointer in `NativeFindServiceHandle` without a Drop implementation. Dropping the returned outer future before its first poll therefore does not run `ServiceDiscoveryFuture::drop`, despite having already started native discovery.

This is a baseline ownership gap, not a new measured failure, but reusing that shape for Any cannot support the plan's unconditional cleanup guarantee. Require immediate ownership of every successful start through a stop guard that survives return, or defer native start until first polling and establish ownership immediately then. Cover never-polled drop, polled-pending cancellation, successful completion and start failure, verifying exactly one stop where start succeeds. Retained builders/proxies must still remain valid after stopping discovery.

Also, `consumer.rs:1031–1049` returns Ready for the first received handle container, including an empty one. The future completes and stops its search; it is not a continuous stream. Plan line 316's initial empty result followed by later update cannot occur through the same already-completed future. Define and test one-shot/repeated-query semantics or a genuinely pending operation without silently changing Specific behavior. #1261's continuous heterogeneous stream remains excluded.

## P2 — the descriptor fallback cannot express absent identity as promised

Plan lines 260–274 offer either changing `ConsumerDescriptor::get_instance_specifier` to a Result or retaining its total `&InstanceSpecifier` return while adding a fallible accessor. Native `concept.rs:592–595` requires the reference-returning method. For an Any-discovered unconfigured producer, the native handle does not contain its producer InstanceSpecifier. A total reference accessor cannot return absence: it must provide some reference, fail/panic, or change its contract. The fallback's simultaneous promises of no fabricated identity and no Any panic are therefore incomplete.

Choose and implement an explicit reviewable API contract. A fallible signature is a public source compatibility change and needs all implementations/callers updated and measured; an additive fallible accessor must honestly preserve/document any legacy limitation rather than claim the old accessor is safe for every Any result. Distinct concrete native instance identity must remain available for selecting/building multiple consumers; returning ServiceNotFound for a missing producer specifier is an accessor limitation, not failure to discover the service. No descriptor decision is accepted by this supervisor.

## P3 — positive integration must distinguish genuine Any from Specific enumeration

Plan lines 293 and 314 propose adding both BigData instances to the common configuration. Two successful results with both instances configured would not distinguish genuine wildcard crawling from looping over configured Specific entries. Require an actually offered same-interface instance whose ID is absent from the consumer's configured instance set; the provider may use separate configuration. The discovery must use the new Any FFI path, return both actual identities and build/use working proxies. This is the regression that demonstrates genuine per-service wildcard behavior.

Exclusion at line 315 requires an actually offered other-interface service, not merely another configuration entry. Empty/no-offer, new-offer timing, Specific compatibility and native errors must have observable assertions. Retain a builder after dropping discovery and construct/use its proxy, covering both sync-return lifetime and async completion/cancellation where appropriate. A no-crash check alone is not proof of callback quiescence or exactly-once stop; provide counters/native unit evidence where deterministic observation requires it.

Plan line 313 maps a mock-bridge runtime test to `score_com_concept-test`; that target tests the concept crate, not automatically new LoLa runtime unit cases. Added tests must be attached to real native BUILD targets. Lines 322/371 use `...` as a native label placeholder; independently discover the concrete rule before measurement. The current operator driver accepts positive regression plans only beneath `basic_rust_api`, so the planned C++ reference target needs explicit check inventory or an omission disposition. Merely listing it in prose does not execute it.

C4 from the contract review remains applicable: missing regression-plan presence now fails the check stage, but model-provided labels do not prove genuine positive semantics. Raw native cases and changed test source must substantiate the obligations; no wrapper/stub-only coverage can establish completion.

## P4 — selection, stable storage and allocation need precise limits

Runtime-owned deque/cache storage can keep wildcard deployment pointers valid beyond synchronous calls, discovery drop and emitted proxy lifetimes. Verify cache uniqueness, stable references and destruction order: storage must outlive service-discovery/binding operations that use it. The config-owned service-type reference must also remain valid. The mandatory lifetime refinement is reflected in plan lines 230–234 and 335–337, but these remain implementation obligations.

Plan lines 207–219 select the first configured instance matching a service short-name and copy its ASIL/event/binding metadata. Native `configuration.cpp:411–420` returns a set of specifier names matching `service_.ToString()`; this is not evidence that all matching deployments have compatible version, quality and bindings. The first lexical instance must not silently define a wildcard across incompatible deployments or reject a valid LoLa mapping merely because another binding was first. Resolve compatible selection, reject ambiguity or explicitly constrain/document the supported universe, with native tests. Snapshot caching and later AddConfiguration behavior must follow that same rule.

The first-query copy/deque/cache operations allocate, and the proposed `resolve_any` is noexcept. Plan lines 341–342 cannot claim initialization-only/no run-phase allocation unless synthesis is actually performed before the running phase. Record actual allocation timing and termination/failure behavior; do not infer bounded safety properties from a one-per-type cache. Adding a non-pure IRuntime virtual preserves source compilation of existing mocks in principle but changes the vtable ABI, so the plan's “additive only” wording is not a binary compatibility guarantee.

## Supported parts and remaining verification

The plan correctly preserves typed interface I scope, excludes #1261's public heterogeneous API, uses real LoLa instance-id-less discovery, proposes additive interface registration metadata, avoids a concrete Runtime cast, preserves existing three-argument registration and retains pending offline acceptance. Unknown/unmapped interface, empty success and underlying discovery failure must remain distinct enough for the documented contract; existing async `FailedToStartDiscovery` behavior should not accidentally be replaced by a coarse synchronous error mapping.

The proposed runtime stable store is preferable to stack/local wildcard deployment ownership. It must still be demonstrated through actual returned-handle/proxy behavior. Added FFIBridge methods and descriptor changes require mock/external implementation compatibility analysis. Exact compiler/FFI layouts, no unwind across C ABI, callback lifetime/stop errors, source/lock/policy/license preservation and selected analyzer execution remain for final patch/evidence review. Native requirement/ticket citations remain unresolved source references, not accepted trace links.
