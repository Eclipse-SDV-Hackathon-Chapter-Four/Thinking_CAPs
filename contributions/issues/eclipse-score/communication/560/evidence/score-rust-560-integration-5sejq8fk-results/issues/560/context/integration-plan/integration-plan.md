## Coordination and callback observations

The controlling main thread owns its runtime, discovery, consumer and subscription. Do not move native handles between threads to make orchestration easier. The provider child owns a separate LoLa runtime and offered producer. Both processes run inside the same integration image and package cwd, using `etc/config.json`.

Use a narrow line protocol on provider stdin/stdout: OFFER, WITHDRAW, SEND(marker), FINISH commands and matching acknowledgements tagged with phase numbers. These are proposed test protocol messages, not existing native APIs. Use a unique protocol prefix; validate prefixed messages' phase, command and completion status while retaining non-protocol native diagnostics separately. Emit test diagnostics on stderr. Native logging must not impersonate an acknowledgement. Flush acknowledgements before awaiting the next command. The controller must deadline-bound reads and reject EOF, malformed/out-of-order protocol messages, unexpected child exit and timeout. A blocking `read_line` alone does not meet this requirement: a reader thread can report through a channel while the controller uses `recv_timeout`; it owns no native handles and must be joined after killing/waiting its owned child on failure. The integration fixture supplies an outer timeout as well. Drain child stderr concurrently or inherit it; an unread full stderr pipe must not block the provider.

Before registration, use bounded discovery and wait until the subscription query reports Subscribed. Registration does not promise an immediate current-state notification: the native setter stores the handler without calling it. Never wait for or require such an initial callback. Once registration succeeds, WITHDRAW makes the child call `offered.unoffer()`. It must stay unoffered until the controller receives a real pending callback and checks the synchronous query. Only then issue OFFER and await the subscribed callback and query. The same consumer/subscription survives the cycle: rediscovery/resubscription would invalidate the auto-reconnect assertion.

Capture a unique handler ID, a thread-safe observation sender and a captured DropProbe in each handler. Record state and invocation count quickly, without calling any subscription method, doing I/O, panicking or waiting on the controller. Use a non-capacity-blocking channel; record send failures in test-owned atomics and report them from the main thread. DropProbe records exactly one destruction for that handler ID. Ensure it is genuinely captured and used by the closure; merely constructing a probe outside the closure does not measure callable disposal.

Maintain separate callback, destruction and protocol records with ordered phase identifiers. Callback records can arrive before the callback returns or C++ destroys it: receipt of a callback alone is not a destruction fence. For false-return tests, await DropProbe destruction and use a synchronous state query from the controller as the native state-lock fence before teardown. For replacement/unset, the returning native setter/unsetter is the synchronization boundary. Snapshot counts after it returns; flag any later invocation of the removed ID.

No fixed sleep authorizes the next provider phase. Query/discovery polling outside the handler may use bounded backoff, with absolute deadlines and complete observed states retained; it does not replace callback receipt in the notification test. For negative callback assertions, prove the subsequent pending/subscribed transitions using query observations and a positive-control handler/sample cycle; silence or a process exit alone is insufficient. Check at phase boundaries and final cleanup. A finite schedule establishes only that schedule, not race absence.

## Proposed integration cases

The names below are local planning/test names, not invented native requirement identifiers. Each pytest case starts a fresh binary and runtime pair.

1. **`test_subscription_state_notifications` (supervisor O12/G8).** Find and subscribe to the offered service; record initial Subscribed. Register a retaining handler. WITHDRAW; receive SubscriptionPending from the real Rust callback, verify the query, and keep the provider withdrawn until these assertions finish. OFFER; receive Subscribed on the same subscription, verify the query, and receive a fresh generation-marked sample. Explicitly unset and require exactly one captured-resource destruction. This is the primary missing production Rust→C++→Rust proof. Do not require an exact total callback count if internal transitions can emit duplicate public states; retain the entire trace and assert the ordered phase-specific pending/subscribed observations.

2. **`test_subscription_state_handler_replacement` (G7/G8 replacement).** With a stable subscribed provider, set handler A then B. After B's setter returns, require A's captured resource to be destroyed once. Withdraw/re-offer under B's phase acknowledgements and require B's pending/subscribed observations and query agreement, with no later A invocation. Unset B; require B destruction once. Drop the subscription and require both counts still one.

3. **`test_subscription_state_handler_unset` (unset guarantee).** Set A then unset it while subscribed. Returning unset and a one-count DropProbe establish its disposal boundary. Withdraw and hold until the main-thread query reports pending, then re-offer and query subscribed; require no post-unset A invocation. Register B and perform a callback-observed positive-control cycle, then unset B. A and B must each be destroyed once, with no captured samples held during cleanup.

4. **`test_subscription_state_handler_false_then_drop` (G6/G8 cancellation).** Set A to record the first controlled pending transition and return false. Hold the provider unoffered; await pending observation, A destruction and main-thread pending query. Re-offer and verify subscribed/query plus a fresh sample, requiring no further A invocation. Drop the same subscription so its still-true Rust handler flag exercises redundant native unset followed by unsubscribe. Destruction remains exactly one; complete without crash/hang. This covers the current LoLa backend, not hypothetical failure-after-consumption by a future FFIBridge.

5. **`test_subscription_state_handler_drop_active` (teardown).** Set A on a stable subscribed service and drop the subscription with A still registered, after releasing all samples. Require one captured-resource destruction and no later A callback. Create a fresh consumer/subscription with positive-control handler B and drive a verified provider withdrawal/re-offer cycle. Destroy B and require one disposal for each ID. The old subscription must not be accessed after drop. This observes production cleanup but does not independently establish the internal unset-before-unsubscribe call order already measured by a mock unit test.

Each case records successful protocol termination and child exit, observations, destruction counts and any failures. On any failed assertion or deadline, explicitly terminate and wait the owned child, close pipes, join reader threads, and let native resource ownership unwind within the test process. Do not signal stale PIDs or unrelated services. Use separate fresh processes per scenario so previous callbacks, SHM state or global runtime state cannot satisfy another scenario.
