A dependent component requirement can,\nhowever, declare that it implements a received AoU by referencing it from its own\n``derived_from`` field (see `AoU Forwarding`_ below).\n\n.. code-block:: text\n   :caption: examples/seooc/docs/aous.trlc\n\n    package SampleType\n\n    import ScoreReq\n\n    ScoreReq.AoU SampleAoU {\n        description = \"It shall be made sure that shared memory segments are never created with the wrong name (ShmemCreatedWrongName)\"\n        safety      = ScoreReq.Asil.B\n        version     = 1\n    }\n\n.. code-block:: starlark\n   :caption: examples/seooc/docs/BUILD and examples/seooc/BUILD\n\n   assumptions_of_use(\n       name = \"sample_aous\",\n       srcs = [\"aous.trlc\"],\n   )\n\n   dependable_element(\n       name = \"safety_software_seooc_example\",\n       assumptions_of_use = [\"//docs:sample_aous\"],\n       ...\n   )\n\nPreventing a root cause\n-----------------------\n\nAn own ``AoU`` closes a root cause of a ``safety_analysis`` fault tree by\nreferencing the generated ``RootCause`` record in ``root_causes``:\n\n.. code-block:: text\n   :caption: aou.trlc\n\n    package SampleType\n\n    import ScoreReq\n    import sample_safety_analysis_fta\n\n    ScoreReq.AoU SampleAoU {\n        description = \"The user shall provide a correct configuration\"\n        safety      = ScoreReq.Asil.B\n        version     = 1\n        root_causes = [sample_safety_analysis_fta.UserProvidedWrongConfiguration]\n    }\n\nThe generated ``<fta_package>`` package only exists as output of the\n``safety_analysis`` target, so two attributes must name that target:\n\n.. code-block:: starlark\n\n   safety_analysis(\n       name = \"sample_safety_analysis\",\n       safetymeasures = [\"aou.trlc\"],  # counts the AoU as a measure of the root cause\n       # ...\n   )\n\n   assumptions_of_use(\n       name = \"sample_aous\",\n       srcs = [\"aou.trlc\"],\n       deps = [\":sample_safety_analysis\"],  # resolves sample_safety_analysis_fta\n   )\n\nAn own AoU is never a ``derived_from`` source of a ``CompReq``; only AoUs\nreceived from another dependable element are (see `AoU Forwarding`_).\n\nAoU Forwarding\n--------------\n\nWhen a dependable element depends on another via ``deps``, all **assumptions of\nuse** defined by the dependency are automatically forwarded to the dependee.\nThis ensures the integrating project is made aware of every condition it must\nsatisfy — even those originating from transitive dependencies.\n\nThere are two forwarding mechanisms:\n\n**Automatic forwarding (own AoUs)**\nAll AoUs declared in a dependable element's ``assumptions_of_use`` attribute are\nautomatically forwarded to every element that lists it in ``deps``. No\nconfiguration is needed.\n\n**Chain-forwarding (received AoUs)**\nWhen a dependable element receives forwarded AoUs from its own dependencies, it\ncan selectively forward them further by providing an ``aou_forwarding`` YAML\nfile. Each entry requires a mandatory justification explaining *why* this AoU\nis forwarded rather than handled locally:\n\n.. code-block:: yaml\n   :caption: examples/seooc/aou_forwarding.yaml\n\n    forwarded_aous:\n      - aou_id: \"OtherLibrary.TimingConstraint\"\n        justification: >\n          This SEooC is a library component and has no control over the\n          invocation cycle time. The system integrator must ensure that\n          calls to the library do not exceed the 10ms cycle time constraint\n          imposed by the underlying other_seooc dependency.\n\n**Handling AoUs received in the dependee**\nEvery AoU a dependable element receives appears as\nan item in a \"Received AoUs\" tier in the dependee's lobster traceability\nreport. Each received AoU must be covered by exactly one of:\n\n- **Handling it locally**: a component requirement's ``derived_from`` field\n  references the AoU it implements (see below). This shows up as \"Component\n  Requirements\" coverage in the report.\n- **Chain-forwarding it further** (with justification) via ``aou_forwarding``,\n  to be handled by this element's own dependees instead. This shows up as\n  \"Forwarded AoUs\" coverage in the report.\n\nIf a received AoU is neither handled nor forwarded, the ``bazel test``\ntraceability check fails.\n\nA single dependable element can do all three at once — receive AoUs from its\nown dependencies, handle some of them locally, chain-forward the rest, and\nstill contribute its own AoUs to the mix:\n\n.. uml:: ../_assets/aou_forwarding_one_seooc.puml\n\n**Handling a received AoU with a component requirement**\nAdd a typed, versioned reference to the AoU (``Package.RecordName@version``,\nmatching the upstream ``AoU`` TRLC record) to the ``derived_from`` field of\nthe ``CompReq`` that implements it, alongside any ``FeatReq``/\n``AssumedSystemReq`` references — all three item kinds share the same field.\nTwo things are required for the reference to resolve:\n\n1. ``import`` the AoU's package, same as any other TRLC cross-reference.\n2. List the ``assumptions_of_use`` target that defines (or, for a received/\n   forwarded AoU, originally defined) the record in the\n   ``component_requirements`` target's ``deps``. This target provides\n   TrlcProviderInfo, so it can be listed directly -- no intermediate wrapper\n   is needed.\n\n.. code-block:: text\n   :caption: :header-rows: 1\n   :widths: 18 47 35\n\n   * - Type\n     - Description\n     - Traceability\n   * - **AssumedSystemReq**\n     - Requirements from the user / assumed system towards the SEooC.\n\n must be explicitly updated.\n\nWriting Good Requirements\n-------------------------\n\nThe rules only check that requirements are *well-formed and traceable* — not that\nthey are *well-written*. The authoritative writing rules live in the\n`Requirements Writing Guidelines <https://github.com/eclipse-score/tooling/blob/main/validation/ai_checker/guidelines/requirements/requirements_guidelines.md>`_\n(the same guidelines the AI quality check applies) and the S-CORE\n`Requirements Engineering process area <https://eclipse-score.github.io/process_description/main/process_areas/requirements_engineering/index.html>`_.\n\nThe guideline document defines: a mandatory **sentence template** for every requirement; a set\nof **quality criteria** (unambiguous, verifiable, atomic, consistent, complete, necessary) with\nterms and patterns to avoid; a short explanation of the **requirement types** (functional,\ninterface, non-functional, process) and how each is verified; and a list of **pre-flight checks**\nthat the AI quality check applies before raising a finding (e.g. not flagging formally defined\ndomain terms as vague, or intentional design constraints as level mismatches). The essentials are\ndistilled below.\n\nSentence template\n~~~~~~~~~~~~~~~~~~\n\nEvery requirement follows one structure — **subject** *shall* **verb** [*object*]\n[*parameter*] [*condition*] — with at least one of object / parameter / condition present:\n\n    The component *shall* detect if a key-value pair got corrupted and set its status to\n    ``INVALID`` during every restart of the SW platform.\n\nQuality criteria\n~~~~~~~~~~~~~~~~~~\n\n- **Unambiguous** — one interpretation. Prefer ``:term:`` glossary nouns over pronouns and\n  vague words (*fast*, *efficient*, *as appropriate*).\n- **Verifiable** — a test or review can objectively pass or fail it.\n- **Atomic** — one ``shall``; split \"and\"/\"or\" and unbounded lists (*etc.*, *and so on*).\n- **Consistent** — no contradiction with other requirements.\n- **Complete** — has subject + verb + at least one of object/parameter/condition, and fully\n  specifies behaviour *at its own level* without pre-empting lower-level detail.\n- **Necessary** — traces to a parent or a ``rationale``.\n\nUse *shall* for obligations; put non-normative notes in the ``note`` field, not\n``description``. Keep implementation detail out of system/feature requirements — but an\n*intentional* design constraint (mandating a transport, mechanism, or safety property) is a\nlegitimate requirement, not a level violation.\n\nChoosing the level\n~~~~~~~~~~~~~~~~~~~~\n\nLevels differ by **scope and observer**, not wording:\n\n- **AssumedSystemReq** — the need comes from *outside* the SEooC; describes it as a black box.\n- **FeatReq** — spans **several** components on one feature; phrased against the public\n  interface, solution-neutral.\n- **CompReq** — fully implementable and testable **inside one component**.\n\nIf the level is unclear, discuss the boundary with the requirements owner — it drives\nallocation and traceability.\n\nRefining a parent into children\n~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~\n\n``derived_from`` is a refinement claim: each child is a narrower, consistent refinement; the\nchildren together must be **sufficient** to satisfy the parent; a child inherits the parent's\n``safety`` level unless a lower one is justified. On any content change, bump ``version`` and\nre-pin every child (``@1`` → ``@2``).\n\n.. code-block:: text\n\n    # Weak — unverifiable, multi-concern, leaks implementation\n    \"The manager should quickly handle values and store them efficiently in a hash map.\"\n    # Better — atomic, verifiable, follows the template\n    \"The numeric value manager shall return the most recently stored uint8_t value on every read access.\"\n\nModeling Requirements\n---------------------\n\nAll requirements are written in `TRLC <https://github.com/bmw-software-engineering/trlc>`_\n(Traceability Requirements Language Checker). it is converted to an RST\n``.. image::`` directive:\n\n.. code-block:: text\n\n    ScoreReq.CompReq COMP_002 {\n        description = '''The system shall expose the following architecture.\n\n        ![Architecture overview](diagrams/arch.svg)'''\n        safety       = ScoreReq.Asil.B\n        derived_from = [MySeooc.FEAT_001@1]\n        version      = 1\n    }\n\n**PlantUML diagrams** — write a raw ``.. uml::`` RST directive;
