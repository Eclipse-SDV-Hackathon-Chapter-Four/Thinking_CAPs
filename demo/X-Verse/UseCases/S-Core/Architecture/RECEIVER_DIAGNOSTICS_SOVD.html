1 · Feature overview

The ADAS S-CORE ECU (cruise control) now carries a receiver-diagnostics vertical served through the Eclipse openSOVD stack. The ECU stamps every speed-signal reception and acceptance inside its control loop and, on each 50 ms control tick, emits a compact diagnostic observation over a Unix datagram socket. The app stays a pure detector — it only reports what it received and accepted. Everything diagnostic lives in score::mw::diag / openSOVD: the application-owned cruise-control-diag server, built only on the public eclipse-score/inc_diagnostics platform API (PR #16 branch; the platform opensovd-gateway stays unchanged) consumes the observation stream, applies TimeBased debounce semantics from score::mw::diag::dtc, qualifies DTC CC.LostCommunication and serves it — with the live speed and cruise state — as diag_api DataResources through the opensovd-server SOVD HTTP API, adapted by PR-16's sovd_adapter. Emission is strictly non-blocking: a dead or missing diagnostics peer can never stall the controller.

Demonstrated live with the real Zenoh→SOME/IP simulation: an I-press in manual controls dropped the speed message from the network → within ~1 s the DTC went confirmed / failed; restoring the signal healed it back to passed. Recorded timelines (f005 through the inc_diagnostics gateway); control behaviour untouched.

received / accepted clocks are stamped per event inside the input receive handler; observed_at at emission. The ordering the provider validates (received ≤ accepted ≤ observed) therefore holds by construction. Datagrams are ≈600 B against a 4096 B cap that both ends enforce. If the socket is missing, full or closed, the non-blocking send just drops the sample — the control loop keeps running.

2.3 Fault lifecycle — CC.LostCommunication

stateDiagram-v2
    [*] --> unknown
    unknown --> startup : power-on grace · 2000 ms
    startup --> healthy : heartbeat + speed budget met
    startup --> failed : no accepted speed after grace — cold stack expectation
    healthy --> pending_failure : freshness stale · speed budget 1000 ms
    pending_failure --> failed : debounce · 100 ms
    pending_failure --> healthy : signal returns
    failed --> pending_recovery : signal returns
    pending_recovery --> healthy : recovery hold · 150 ms
Parameter (env at container start)DefaultMeaning
CRUISE_SIGNAL_BUDGET_MS1000accepted-speed freshness budget
CRUISE_STARTUP_GRACE_MS2000no fault during boot
CRUISE_DEBOUNCE_FAILED_MS100TimeBased debounce before failed
CRUISE_DEBOUNCE_PASSED_MS150recovery hold before recovered

The debounce is score::mw::diag::dtc::Debounce::TimeBased semantics implemented on top of diag_api in score/examples/cruise_control_diag/src/lib.rs — not a bespoke state machine. An observation whose speed field is null (datagram landed, nothing accepted in that tick) prefails immediately (the receiver sees the stream, not the signal); a datagram older than the signal budget fails; nothing at all after the boot grace fails. The eclipse gateway is stateless in-memory (fault read from the observation link on every request) — persisting DTC state across ECU restarts is future diag_api work.

2.4 Software identity & provenance

Every observation carries software_identity: sha256:<digest> of the running cruise_control_main, computed by the entrypoint at every container start (SCORE_BUILD_IDENTITY) — it cannot drift from the deployed binary. The gateway validates each datagram (schema 1, matching source_instance=cruise-control, matching the current boot_id, monotonic clock ordering received ≤ accepted ≤ observed) and rejects foreign or malformed datagrams before they can touch the fault lifecycle.

2.5 Eclipse alignment — S-CORE-native vs. interim seam

LayerEnd-state S-CORE shapeThis release
app → diagapp reports observations in-process via its component's diagnostic portinterim: env-gated Unix-datagram link (SCORE_DIAGNOSTIC_SOCKET), non-blocking, dormant by default

diag_api is Rust-only today and the ECU app is C++ (no C++ binding, no mw/diag in the ECU tree yet), so a transport between the two is required; the datagram link is that interim seam. When S-CORE ships a C++ diag report port, the app instrumentation stays as-is and the gateway integration collapses into diag-stack configuration.

7 · Design guarantees & limitations

  • Control is never blocked or altered — non-blocking datagrams, best-effort delivery; controller decisions, acceptance semantics and throttle behaviour untouched by the patch.
  • Acceptance is decode-level — decoded_by_consumer, explicitly not E2E or functional plausibility approval.
  • Provenance is verifiable — boot_id, monotonic clock domain, binary sha256; tampered or foreign observations are rejected and counted.
  • Fail-safe defaults — unset SCORE_DIAGNOSTIC_SOCKET ⇒ instrumentation fully dormant.
State openly to judges: freshness budgets are provisional; the catalog contains one fault (CC.LostCommunication), served as a diag_api resource under /components/cruise_control/data/cc_lost_communication, not native /faults; sequence IDs and native E2E protection not yet on this path; a cold stack with no simulation attached trips the fault after boot grace — by design, not a defect; the eclipse gateway holds DTC state in memory only (no KVS persistence yet), a restart starts clean; data endpoints return HTTP 500 until the first observation arrives; cc_fault_injection provides deterministic test forcing.
